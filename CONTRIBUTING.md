## Ways to contribute

Not every contribution is a pull request. Here's how to help at any skill level:

| Contribution | How |
|---|---|
| 🐛 **Report a bug** | Open an issue using the [bug report template](.github/ISSUE_TEMPLATE/bug_report.md). Include logs, your `config.json` (redacted!), OS and versions. |
| 💡 **Request a feature** | Use the [feature request template](.github/ISSUE_TEMPLATE/feature_request.md). Explain the *problem* you're solving, not just the solution. |
| 🧪 **Test & triage** | Reproduce issues, confirm fixes, and add repro steps to existing reports. |
| 📝 **Docs** | Improve the README, extension `SETUP.md`, or Cloudflare guide. Docs PRs are treasured. |
| 🧹 **Housekeeping** | Clean up dead code, improve logging, tighten tests, bump dependency ranges. |
| ⭐ **Spread the word** | Star the repo, share it, use it, and tell us what breaks. |

## Getting started

### 1. Fork & clone

```bash
# Replace OWNER with your GitHub username
git clone https://github.com/OWNER/REPO.git
cd REPO
git remote add upstream https://github.com/OWNER/REPO.git
git checkout -b feat/your-change
```

### 2. Find something to work on

Look for issues labeled `good first issue` or `help wanted`. No issue yet? Open one *before* writing code so we agree on the approach — it saves wasted effort on both sides.

### 3. Set up your environment

```bash
# Python 3.10+ required
python --version

# (Optional) streaming support
pip install httpx

# Copy the example config — never commit your real config.json
cp config.example.json config.json
```

Run the server:

```bash
python -m gemini_web2api        # package edition (recommended)
# or, for a copy-anywhere single file:
python gemini_web2api.py        # bundled edition (generated by bundle.py)
```

Load the browser extension from `chrome://extensions` / `brave://extensions` in **Developer mode** → **Load unpacked** → select `gemini-cookie-sync-extension/`. Bump its version in `manifest.json` when you change it.

## Branch naming

Match the intent with a type prefix:

```text
feat/auto-model-routing        feature
fix/stream-close-race          bug fix
docs/docker-arm64-guide        documentation
perf/stream-buffer             performance
chore/cleanup-tests            housekeeping
```

Never commit directly to `main` — always work on a branch and open a PR.

## Commit conventions

Use [Conventional Commits](https://www.conventionalcommits.org). This keeps `git log` scannable and enables future changelog tooling.

```text
feat: add auto model routing
fix(server): close SSE stream on client disconnect
docs(readme): add Cloudflare deployment section
test(extension): cover popup mismatch state
```

- **Type** is one of `feat`, `fix`, `docs`, `perf`, `test`, `chore`, `refactor`, `build`, `ci`.
- **Scope** (optional) is the area you touched: `server`, `extension`, `cloudflare`, `readme`, `config`, `docker` …
- Keep the subject under ~72 characters, imperative mood, no trailing period.
- One logical change per commit. Squash WIP commits before pushing.

## Code style & project conventions

Respect the project's deliberate design choices:

### 🐍 Python — stdlib first

The project's identity is **zero required dependencies** (only optional `httpx` for streaming). Before adding a dependency, ask: *can this be done with the standard library?* Usually, yes.

- Target **Python 3.10+** — modern syntax (`X | None` unions, walrus) is fine, but keep the stdlib-only rule above.
- Use `http.server`, `urllib`, `json`, `threading` — they're already there.

### 📦 Package is the single source of truth

`gemini_web2api/` is the only place server code lives. `gemini_web2api.py` is **generated** from it by `bundle.py`:

```bash
python bundle.py          # edit the package -> regenerate the single file
python bundle.py --check  # exit 1 if the committed single file is stale
```

**Any change to routing, endpoints, auth, streaming, or config goes in the package only**, then regenerate. `test_suite.py` includes a drift check that fails the battery if `gemini_web2api.py` ever diverges from the package.

### ⚙️ Config-driven, not hardcoded

New behavior belongs behind a key in `config.json` (documented in the README [Configuration](README.md#-configuration) table) — not a magic constant. Keep the schema additive and backward-compatible.

### 🧩 Extension

- Manifest **version must be bumped** on every change (popup, background, or manifest itself).
- Keep the popup's status + Connection settings tests in sync (`test_popup.js`).
- Loopback-only `host_permissions` — never widen them without discussion.

### 🧪 Tests are mandatory

Any behavioral change ships with tests — no exceptions. Server changes get Python tests; extension changes get Node tests. See [Testing](#testing).

## Testing

Run the **full battery** before opening a PR. All of it must pass.

```bash
# One command — the full battery (Python + Node + bundle drift)
python run_all_tests.py              # full battery — auto-starts the server on :8081 if free,
                                     # stops only the watchdog it started; existing server untouched
python run_all_tests.py --offline    # unit-only + mocked integration (CI-safe)

# …or individual suites
python test_suite.py            # main battery — API, auth, models, config (103 tests)
python test_integration.py      # ephemeral-port integration test (Gemini mocked)
python test_proxy_fallback.py   # proxy fallback on 429/errors (6 tests)
python test_cookie_refresh.py   # cookie-refresh endpoints & CLI (14 tests)
python test_watchdog.py         # watchdog health analysis (44 tests)
python test_run_all.py          # orchestrator auto-start logic (8 tests)
python test_autostart.py        # autostart health summary (15 tests)
node test_extension.js          # background service worker (70 tests)
node test_popup.js              # popup dashboard + Connection + Server health (46 tests)

# Bundler + syntax sanity
python bundle.py --check        # single file == package (no drift)
python -m py_compile gemini_web2api.py gemini_web2api/*.py bundle.py
node --check gemini-cookie-sync-extension/background.js
node --check gemini-cookie-sync-extension/popup.js
```

**When you add a feature**, add a test that covers it (and its failure mode). **When you fix a bug**, add a test that reproduces the bug first — then make it pass.

## Pull request process

1. **Fork** the repo and create your branch (`feat/…`, `fix/…`, `docs/…`).
2. **Write/update tests** for your change — the suites above must pass.
3. **Run the full test battery** (`python test_suite.py` + the node suites) locally.
4. **Open a PR** using the [pull request template](.github/PULL_REQUEST_TEMPLATE.md). Keep diffs focused — one concern per PR.
5. A maintainer reviews within a few days — be ready for feedback. 🚀

### PR checklist (before you submit)

- [ ] Branch name follows `type/description`
- [ ] Commits follow Conventional Commits
- [ ] Server code changed in `gemini_web2api/` only, and `python bundle.py` regenerated the single file
- [ ] `manifest.json` version bumped when the extension changed
- [ ] New tests added; **all** suites pass locally
- [ ] No `cookie.txt`, real `config.json`, or secrets committed
- [ ] README updated when user-facing behavior changed (features, config keys, endpoints)

## Code review

Reviewers will look for correctness, test coverage, and consistency with the conventions above. Be kind and specific in reviews: point at lines, ask questions, suggest. **All CI checks and tests must be green before merging** — maintainers merge, contributors request.

## Security & `cookie.txt`

`cookie.txt` is **your Gemini session** — treat it like a password. It is gitignored for a reason:

- Never commit it, never share it, never paste it into an issue.
- Never commit your real `config.json` (keys, XSRF tokens).
- If you think you've leaked a session, revoke it in Google's security settings immediately.

Report security vulnerabilities privately (see [Security policy](SECURITY.md) if present) — don't open a public issue.
